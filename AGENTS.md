# Инструкции для агента

## Источник

Использовать производственный календарь КонсультантПлюс для нужного года: `https://www.consultant.ru/law/ref/calendar/proizvodstvennye/ГОД/`. Проверять год в заголовке и актуальность утверждённых переносов.

- Из раздела «Нерабочие праздничные дни» брать даты и названия федеральных праздников.
- Из раздела «Перенос выходных дней» брать переносы по постановлению и при совпадении праздника с выходным. У новогодних праздников особый порядок: не применять к ним общее правило автоматически.
- Из комментария и отметок календаря брать сокращённые рабочие дни, учитывая рабочие субботы и переносы; не вычислять их только по дате праздника.

## Обработка данных

Календарь рассчитан на пятидневку. Включать праздники, перенесённые выходные и сокращённые дни. Обычные субботы и воскресенья, региональные и профессиональные праздники не добавлять. Не расширять праздники на целые периоды отдыха. Рождество и новогодние каникулы сохранять раздельно.

Хранить данные в `data/ГОД.json`: `year`, `source`, `events`. У события обязательны `start`, `end` (включительно, `YYYY-MM-DD`), `key`, `title`, `kind`; пояснение — в `description`.

- `holiday` — праздник с названием из источника; сохранять существующие ключи праздников.
- `transfer` — отдельное событие «Перенесённый выходной», `key: "transfer"`; в описании указывать исходную дату переноса.
- `short` — «Сокращённый рабочий день», `key: "short"`; в описании указывать сокращение на час и предстоящий праздник в формате «название, ДД.ММ.ГГГГ».

Старые годы сохранять. Даты задавать явно для каждого года, без ежегодного повторения. Не создавать дубли. Учитывать, что после переноса исходная суббота может стать рабочей.

## Формирование календаря

После изменения данных или генератора запускать `python3 generate.py` (Python 3.9+, без зависимостей). `calendar.ics` вручную не редактировать. Генератор собирает все годы и объединяет только соседние или пересекающиеся `holiday` с одинаковым ключом; переносы и сокращённые дни остаются отдельными.

Сохранять формат ICS: события на весь день (`VALUE=DATE`), исключительная граница `DTEND`, UTF-8, CRLF, строки до 75 байт с корректным сворачиванием и экранированием. Без напоминаний (`VALARM`), с `TRANSP:TRANSPARENT`. Источник указывать один раз в последней строке `DESCRIPTION`, без поля `URL`, чтобы Apple Calendar не показывал отдельную кнопку открытия ссылки. Для праздников в `DESCRIPTION` оставлять только ссылку. UID формировать из ключа и даты начала; без необходимости их не менять. Временные метки обновляются при генерации.

Проверять даты и исходные даты переносов, отсутствие дублей и пересечений выходных с сокращёнными днями, уникальность UID и формат ICS. Годовые итоги сверять с источником, учитывая обычные выходные и рабочие субботы только при подсчёте. Корректные CRLF и пробелы сворачивания не удалять ради `git diff --check`; исходники проверять отдельно.

## Публичная информация и публикация

В `README.md` оставлять только ссылки на подписку и загрузку, дату обновления календаря и охваченные годы. При обновлении календаря актуализировать дату, при добавлении года — диапазон в README и `index.html`. Технические инструкции хранить здесь.

Сохранять имя `calendar.ics` и адрес публикации `https://alexandrdev.github.io/production-calendar-ru/calendar.ics`; для подписки использовать схему `webcal://`.

При публикации коммитить данные, пересобранный ICS и связанные правки, отправлять в `main`. Не включать `.DS_Store` и посторонние изменения. GitHub Pages публикует файл, подписки получают его при следующем обновлении. Не сообщать об успешной отправке до завершения push.

## Автоматическое обновление и настройка GitHub Actions

### Что запускается

Workflow `.github/workflows/calendar.yml` проверяет **следующий год 1 декабря в 09:17 по Москве** (`17 6 1 12 *`, UTC). Например, 1 декабря 2026 года проверяется 2027 год. GitHub может задержать запуск; точное время не гарантируется.

`update_calendar.py` работает на Python 3.9+ без сторонних библиотек. Он загружает HTML, проверяет год в заголовке и наличие утверждённого постановления, читает федеральные праздники и переносы из комментария, сокращённые дни — из таблиц с дополнительной сверкой по комментарию. Проверяет все дни календаря и годовые итоги. Обычные выходные и рабочие субботы используются только для сверки. При неизвестной структуре, проекте постановления, несовпадении дат или итогов скрипт завершает работу с ошибкой до записи файлов. Необычные переносы (например, между годами или на субботу) требуют ручной поддержки парсера.

При изменении данных скрипт обновляет только выбранный `data/ГОД.json`, диапазон лет и дату в README, диапазон в `index.html`, затем запускает `generate.py`. При ошибке генерации восстанавливает прежние файлы. Если данные совпадают, ICS и дата обновления не меняются. Старые годы автоматически не перепроверяются.

Workflow проверяет тесты, сохраняет изменения коммитом в `main` и сам публикует `index.html` и `calendar.ics` в Pages. Публикация также выполняется при обычном push этих файлов или самого workflow в `main`. Технические файлы в артефакт сайта не включаются. При ошибке парсинга публикация не выполняется, опубликованный календарь остаётся прежним.

### Первоначальная настройка на GitHub

1. Сначала отправить новые файлы в GitHub: пока `.github/workflows/calendar.yml` существует только локально, workflow **Calendar** во вкладке Actions не появится. Находясь в ветке `main`, выполнить из корня проекта:

   ```sh
   git add .github/workflows/calendar.yml update_calendar.py tests/test_calendar.py .gitignore AGENTS.md
   git commit -m "Add annual calendar import and GitHub Actions"
   git push origin main
   ```

   Дождаться успешного push и убедиться, что файл `.github/workflows/calendar.yml` виден в ветке `main` на сайте GitHub. Не включать `.DS_Store` и посторонние файлы.
2. Открыть репозиторий → **Settings → Actions → General**. Разрешить GitHub Actions и официальные actions `actions/*`. Если политика репозитория или организации запрещает запись, разрешить workflow запись в содержимое репозитория. Сам workflow запрашивает `contents: write` только для заданий с коммитами. Персональный токен и дополнительные secrets не требуются: используется встроенный `GITHUB_TOKEN`.
3. Убедиться, что **main — default branch**. Расписание работает только из основной ветки; ручные запуски этого workflow также выполнять на `main`.
4. В **Settings → Rules → Rulesets** (или **Branches → Branch protection**) проверить, что правила позволяют этому workflow напрямую отправлять коммиты в `main`. Если обязательны PR или запрещены прямые push, автокоммит и служебные коммиты завершатся ошибкой; потребуется изменить разрешения либо переделать публикацию через PR. Workflow не обходит правила защиты.
5. В **Settings → Pages → Build and deployment → Source** выбрать **GitHub Actions**. Не выбирать Deploy from a branch: коммиты через `GITHUB_TOKEN` сами по себе не запускают сборку Pages. В **Settings → Environments → github-pages** разрешить публикацию из `main`; обязательное ручное подтверждение деплоя отключить, если нужна полностью автоматическая публикация.
6. После успешного push открыть [workflow Calendar](https://github.com/AlexandrDev/production-calendar-ru/actions/workflows/calendar.yml) либо вкладку **Actions** и выбрать **Calendar** в списке workflows слева. На странице выбранного workflow нажать **Run workflow**, выбрать `main`. Поле `year` оставить пустым для следующего года либо ввести нужный год, например `2027`. Нажать **Run workflow**. Пустое поле всегда означает следующий год по текущей московской дате, даже при ручном запуске в январе. Если Calendar отсутствует, проверить загрузку YAML в `main` и разрешение Actions из шага 2. Если отсутствует только кнопка Run workflow, проверить права записи в репозиторий и наличие `workflow_dispatch` в файле на основной ветке.
7. Дождаться успешного завершения `build` и `deploy`. Если данные изменились, проверить коммит `github-actions[bot]` в `main`. Проверить [опубликованный ICS](https://alexandrdev.github.io/production-calendar-ru/calendar.ics) и [страницу подписки](https://alexandrdev.github.io/production-calendar-ru/). Сам адрес подписки остаётся `webcal://alexandrdev.github.io/production-calendar-ru/calendar.ics`.

Стандартные `ubuntu-latest` runners бесплатны для публичных репозиториев; GitHub Pages также доступен на GitHub Free для публичного репозитория. Платный runner и внешние сервисы не нужны.

### Чтобы ежегодное расписание не отключилось

GitHub отключает scheduled workflows в публичных репозиториях после 60 дней без активности. Поэтому в том же workflow предусмотрен **служебный запуск 15-го числа каждого месяца в 09:23 по Москве**. Он не обращается к КонсультантПлюс, не меняет календарь и не публикует сайт. Если последнему коммиту в `main` не менее 40 суток, создаёт пустой коммит `chore: keep annual calendar schedule active`. При исправно работающем расписании это поддерживает активность репозитория между ежегодными обновлениями.

Если workflow уже отключён, открыть **Actions → Calendar → Enable workflow**. Проверять ошибки служебных запусков: если запись в `main` запрещена или Actions отключены, механизм не поддержит активность. Удаление служебного расписания означает, что перед 1 декабря нужно самостоятельно поддерживать активность или включать workflow заново. GitHub не гарантирует доставку cron-запусков; пропущенный ежегодный запуск можно повторить вручную с нужным `year`.

### Локальный запуск и диагностика

```sh
# Следующий год, с обновлением файлов при изменении данных:
python3 update_calendar.py

# Конкретный год:
python3 update_calendar.py --year 2027

# Только загрузить и проверить источник, не меняя файлы:
python3 update_calendar.py --year 2027 --check

# Проверить сохранённый HTML, без сети и записи:
python3 update_calendar.py --year 2027 --html /tmp/consultant-2027.html --check

# Автономные тесты парсера, восстановления файлов и формата ICS:
python3 -m unittest discover -s tests -v
```

Если источник недоступен, переносы ещё не утверждены либо изменилась структура страницы, открыть ошибочный запуск в Actions и прочитать сообщение `Ошибка обновления календаря`. Исправить парсер при необходимости и повторить ручной запуск с тем же годом. Автоматических повторных проверок источника после 1 декабря нет. Если данные обновились и коммит отправлен, но упал только `deploy`, повторный ручной запуск опубликует уже сохранённый календарь без лишнего коммита.
