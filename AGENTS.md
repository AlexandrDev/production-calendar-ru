# Правила работы с производственным календарём

## Назначение и файлы

Календарь России для пятидневной рабочей недели с выходными в субботу и воскресенье. Включает федеральные нерабочие праздничные дни, перенесённые выходные и сокращённые рабочие дни. Региональные, профессиональные праздники и памятные даты не добавлять.

- `data/ГОД.json` — исходные данные за каждый год; старые годы сохранять.
- `generate.py` — генератор на Python 3.9+, без сторонних библиотек.
- `calendar.ics` — общий файл подписки за все добавленные годы; пересобирать после изменения данных или генератора.
- `index.html` — страница подписки; при добавлении года обновлять указанный диапазон лет.
- `README.md` — только ссылки на календарь и инструкции по обновлению. Подробности реализации и правила для агентов хранить здесь.

## Источники и проверка дат

Основной источник — КонсультантПлюс, производственный календарь нужного года:

- [2026](https://www.consultant.ru/law/ref/calendar/proizvodstvennye/2026/).
- [2027](https://www.consultant.ru/law/ref/calendar/proizvodstvennye/2027/).

Перед изменением дат проверять актуальную страницу именно нужного года. Если адрес с годом недоступен, можно использовать корневую страницу календаря, предварительно проверив год в её заголовке. Не выдавать проект постановления о переносах за утверждённые данные.

На странице нужны три источника сведений:

1. «Нерабочие праздничные дни» — названия и собственные даты праздников.
2. «Перенос выходных дней» — переносы по постановлению Правительства и переносы при совпадении праздника с выходным.
3. Комментарий к календарю и отметки предпраздничных дней — сокращённые рабочие дни.

Не путать праздничную дату с целым периодом отдыха из комментария. Обычные примыкающие субботы и воскресенья не включать в события. Перенесённые выходные при этом обязательно учитывать отдельными событиями.

## Праздники

| Даты каждого года | Название | `key` |
| --- | --- | --- |
| 1–6 января и отдельно 8 января | Новогодние каникулы | `new-year` |
| 7 января | Рождество Христово | `christmas` |
| 23 февраля | День защитника Отечества | `defender` |
| 8 марта | Международный женский день | `womens-day` |
| 1 мая | Праздник Весны и Труда | `spring-labour` |
| 9 мая | День Победы | `victory` |
| 12 июня | День России | `russia` |
| 4 ноября | День народного единства | `unity` |

Использовать `kind: "holiday"`. 1–6 января — одно событие, 7 и 8 января — отдельные. Не объединять каникулы и Рождество под общим названием. Если праздник выпадает на выходной, сам праздник остаётся на своей дате, а день отдыха после переноса добавляется отдельно. 31 декабря не является праздником из этого перечня: его статус проверяется для конкретного года.

## Перенесённые выходные

Использовать `kind: "transfer"`, `key: "transfer"`, название «Перенесённый выходной». `start` и `end` равны дате нового выходного. В `description` указывать исходную дату, например: «Выходной перенесён с 03.01.2026.».

Учитывать оба вида переносов:

- По постановлению Правительства для конкретного года.
- При совпадении праздника с субботой или воскресеньем — на следующий рабочий день. Для 1–8 января действует особый порядок: не вычислять переносы автоматически по общему правилу.

Проверенные данные для текущих файлов (при изменении источника сверить заново):

| Год | Исходная дата → новый выходной |
| --- | --- |
| 2026 | 3 января → 9 января; 8 марта → 9 марта; 9 мая → 11 мая; 4 января → 31 декабря |
| 2027 | 20 февраля → 22 февраля; 1 мая → 3 мая; 9 мая → 10 мая; 12 июня → 14 июня; 2 января → 5 ноября; 3 января → 31 декабря |

В 2027 году 20 февраля — рабочая суббота с сокращением на час. Она уже представлена событием `short`; не добавлять на неё событие выходного. При будущих переносах учитывать, что исходная суббота может стать рабочей, и проверять её продолжительность по источнику.

## Сокращённые дни

Использовать `kind: "short"`, `key: "short"`, название «Сокращённый рабочий день». В `description` указывать сокращение на один час и связанный праздник.

- 2026: 30 апреля, 8 мая, 11 июня, 3 ноября.
- 2027: 20 февраля, 30 апреля, 11 июня, 3 ноября.

Не вычислять их простым вычитанием одного дня из даты праздника: учитывать график работы и переносы. 30 декабря 2026 и 2027 годов — полные рабочие дни; выходной 31 декабря сам по себе не даёт сокращения накануне.

## Формат данных и ICS

JSON содержит `year`, `source` и массив `events`. Обязательные поля события: `start`, `end`, `key`, `title`, `kind`; `description` — дополнительные сведения. Даты в JSON имеют формат `YYYY-MM-DD`, обе границы включительны. Данные с сайта автоматически не скачиваются; даты задаются явно для каждого года, без ежегодного повторения.

Генератор объединяет только соседние или пересекающиеся события `holiday` с одинаковым `key`, в том числе между файлами лет. `transfer` и `short` остаются отдельными. Не создавать дубли; одинаковые `key` и дата начала дают одинаковый UID. У одного ключа должно сохраняться одно название.

Сохранять свойства подписки:

- События на весь день: `DTSTART;VALUE=DATE`, `DTEND;VALUE=DATE`. В ICS конечная дата исключительна: генератор прибавляет день к `end` из JSON.
- Без `VALARM`, с `TRANSP:TRANSPARENT`; часовой пояс для дат не нужен.
- Ссылку на источник добавлять один раз в поле `URL` события. Не дублировать её в `DESCRIPTION`; в описании оставлять только сведения о празднике, переносе или сокращении дня. Исходные ссылки сохранять в `source` файлов JSON.
- UTF-8, окончания строк CRLF, перенос физических строк по RFC 5545 до 75 байт, экранирование текстовых значений.
- UID зависит от `key` и даты начала. Не менять ключи без необходимости: изменение ключа или начала меняет UID.
- `DTSTAMP` и `LAST-MODIFIED` меняются при каждой генерации, поэтому побайтовая идентичность повторных запусков не ожидается.
- Сохранять имя `calendar.ics` и адрес публикации: существующие подписки используют этот URL.

## Порядок обновления и проверки

1. Проверить источники, поправить JSON нужных лет. При добавлении года сохранить предыдущие и актуализировать диапазон на странице подписки.
2. Запустить `python3 generate.py`. Не редактировать сгенерированный ICS вручную.
3. Проверить наборы дат, названия, исходные даты переносов, отсутствие дублей и пересечения выходных с сокращёнными рабочими днями. Проверить уникальность UID, границы событий, CRLF, длину строк и отсутствие напоминаний в ICS.
4. Сверить годовые итоги с источником: взять обычные субботы и воскресенья, добавить праздники и перенесённые выходные, исключить ставшие рабочими субботы. Эти обычные выходные нужны только для проверки, в ICS их не добавлять. В текущих данных у каждого года 118 выходных и праздничных дней и 247 рабочих дней, по 4 сокращённых дня; в общем ICS 36 событий. Это контрольные значения для 2026–2027, а не константы для будущих лет.
5. Проверить diff. CRLF в ICS может вызывать сообщения `git diff --check` о пробелах; пробел перед переносом строки также может быть частью текста при сворачивании. Не менять корректный формат ICS ради устранения таких сообщений. Проверку исходных файлов выполнять отдельно.
6. В коммит с обновлением включать JSON, пересобранный ICS и относящиеся к задаче изменения документации, генератора или страницы. Не включать `.DS_Store` и посторонние изменения.

Изменения публикуются через GitHub Pages, подписчики получают их при следующем обновлении. Не утверждать, что изменения опубликованы, пока push не выполнен успешно; создание файла или генерация ICS сами по себе публикацией не являются.
